# Cloud backup and cross-device sync, via Firestore's REST API, a shared-secret save ID, and a merge

The app was local-only on purpose: no backend, no accounts, one browser's `localStorage` as the entire save file. Two things ended that. A new phone, with a year of history stranded on the old one and no way across but exporting a file and importing it by hand. And the plain fact that the history had become worth something. A streak and a level are only meaningful as an unbroken record, and clearing site data by accident would end both. This reverses the local-only commitment deliberately, and this file is where that is owned rather than left implicit in a diff.

**Firestore's REST API, not the Firebase SDK.** This is the decision the rest of the design hangs off. The app ships no runtime dependencies, has no build step, and CI enforces both. One job boots it with `node_modules` deleted. The SDK is around 175 KB gzipped, is not droppable into a plain `<script type="module">`, and adopting it would have meant adopting a bundler, which would have meant rewriting the service worker's explicit shell list, `test/static.test.js`, and the Pages deploy. So `js/sync.js` talks to the same service the SDK does, directly: three endpoints, plain `fetch`, about a page of request shaping. What that gives up is the SDK's offline write queue and its live snapshot listener. Neither is missed here. This app writes roughly once per workout and reads once when it opens, `localStorage` is already the source of truth, and a write that fails costs nothing but a retry when the app next opens or the network returns. The sibling project reached the opposite conclusion for good reasons. It already had a bundler, and its offline write queue was a hard requirement, because a child answers questions continuously while offline. Neither of those is true here.

**A merge, not last-write-wins.** The sibling's equivalent decision took whole-document last-write-wins and accepted losing a few recent attempts in a rare tie. That was right for its data, which is a map of fluency scores, and wrong for this data, which is a log. Almost everything worth keeping in a 5BX save is append-only: every session ever done, every level change. So `js/merge.js` unions the two sides instead of choosing between them, which makes the failure that actually worried me impossible. An old phone, opened once after months in a drawer, cannot overwrite everything logged since. The union is commutative, associative, and idempotent, so devices converge whatever order they sync in and however many times; `test/merge.test.js` asserts all three as properties over generated saves.

**Two things the merge had to get right, both triggered by a phone that installed the app today.** A brand-new device's default save is not empty. It holds Chart 1 D- and a `start` entry in the level log, both stamped with today, which is *newer* than a position earned months ago. Under any "most recent wins" rule that blank default beats the real history. So the current position is not merged at all: it is derived from the merged level log, whose last entry already carries both the position and the instant it was reached. And the level log is modelled as an origin plus a list of changes rather than a flat list, with the origin split out *before* the union rather than de-duplicated after. Splitting it out first is what keeps the merge associative: a discarded origin that happens to share a timestamp with a real level change must not take that change down with it. The property tests found that one; the example tests did not.

**Snapshots, because a mirror is not a backup.** Syncing alone protects against a lost phone and nothing else. A bug, or a bad import, corrupts the save, and every device and the cloud then copy the damage faithfully, with nothing to go back to. So each day's first sync also writes a dated copy to `saves/{saveId}/days/{date}`, and the newest thirty are kept. Restoring one is a replace rather than a merge, and overwrites the stored copy directly rather than going through the ordinary sync. A union would bring the discarded data straight back, which would make the whole mechanism pointless.

**Pairing is a shared-secret link, not an account.** A save lives at `saves/{saveId}`, where `saveId` is a random UUID handed over once as a QR code that a phone's camera decodes straight into "open this link". Anonymous sign-in is required on every request, but only as a cheap deterrent against drive-by bots; it deliberately does not check *which* anonymous user is asking, because every device holding the link is meant to have access and they are all different anonymous users. The real boundary is knowing the exact document path, the same trust model as an unlisted document link.

**That is a real tradeoff, and worth stating plainly: anyone who ever sees the pairing link can read and write this history, forever, with no further check.** Acceptable because the data is one person's record of how many push-ups they did. The alternative, a genuine per-device membership scheme enforced server-side by a Cloud Function, means writing and running backend code for a one-person app, which is the ongoing burden a "no backend" project was avoiding in the first place. `firestore.rules` grants `get`, `create` and `update` on an exact document ID only, and never `list` on the `saves` collection; without that, a signed-in stranger could enumerate every save without guessing a single ID. That absence is guarded by `test/firestore-rules.test.js`, which reads the rules rather than running an emulator, since an emulator would mean `firebase-tools` and a JVM in a suite that has to stay runnable with nothing installed.

**A leaked link cannot produce a bill.** `js/sync-config.js` ships the project ID and API key in the clear, on purpose: Firebase's own design is that these identify the project rather than granting access, and a site with no build step has nowhere to hide them anyway. Because anyone visiting the public site gets an anonymous sign-in the same way, someone could in principle script junk documents at unknown random IDs and burn the daily quota. Staying on the free Spark plan is what bounds that: no card is attached, so abuse fails against a quota rather than arriving as an invoice.

**The theme and the reminder switch never leave the phone.** They describe the device, not the person: which screen you are looking at, and which OS notification permission was granted. They are stripped before sending rather than merely losing the merge, so the stored copy reads the same whichever device wrote it. `settings.updatedAt` is likewise only bumped by settings that travel: counting a theme change would make a phone where nothing else was ever set look like the more recently edited side, and its blank age would then beat the real age set on the other phone.

**Nothing here is shaped for one person, even though the app is.** The app creates exactly one save and shows no way to switch, but the parts underneath are already plural, because the cheapest moment to get that right is before there is data to migrate:

- The Firestore path is `saves/{saveId}`, one document per person. A second person is a second document, which is also why concurrent use can never clobber: two people finishing a workout at the same moment write to two documents with no shared path. A single household document holding everyone would have exactly that failure.
- The device's pairing record is a list with an active entry, not a single ID, so a switcher is a UI addition rather than a stored-format change.
- The remaining piece is `localStorage`, where `5bx-state-v1` holds one person's save under one fixed key. Multiple people means one key each. The migration is that the existing key stays exactly as it is and becomes the first person's; additional people get their own keys. Nothing already stored ever moves, which is the property worth buying now.

Running one clock for two people at once, recording their results separately, needs none of the above to change: it is a workout-view concern that ends in two `logSession` calls against two saves.

Considered and rejected: the Firebase SDK, vendored as a checked-in bundle (an unreviewable 400 KB blob in a repo whose whole pitch is that there isn't one) or loaded from a CDN (breaks the no-CDN rule, and a fresh device would need the network before it could pair); adopting a bundler to use the SDK properly (reverses the project's defining constraint to buy an offline write queue this app does not need); last-write-wins, matching the sibling (a stale device's push would erase newer sessions, which is precisely the loss this exists to prevent); a QR-only handoff with no server (solves the new phone, not the durability, and stops fitting as the history grows past a few kilobytes); syncing the theme and reminder switch (they describe the device); denying deletes to protect against accidents (grants nothing that write access does not already grant, and would make "erase my cloud backup" a promise the app could not keep); emulator-backed rules tests (a JVM and a large toolchain for one small file that a read-the-file guard covers).
